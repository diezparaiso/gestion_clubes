# Database Design

Version: 1.0  
Status: Proposed  
Date: 2026-09-03  
Backend: Supabase PostgreSQL

## 1. Scope

This document defines the first database contract for the multi-club platform. It is based on `Arquitectura_Maestra_Plataforma_Clubes_Flutter.md` and covers the MVP foundation plus the data required to prepare the raffle module.

The database is the security boundary. Every club-owned table is isolated by PostgreSQL Row Level Security (RLS); client-side filters and Flutter routes are not security controls.

The SQL in this document is the intended migration order. Names are in English and `snake_case`.

## 2. Design Rules

- Use UUID primary keys generated by PostgreSQL. Internal identifiers are never reused.
- Every club-owned row has a direct `club_id`, except rows whose parent relation is the security boundary and is explicitly checked by policy.
- Use `timestamptz` for timestamps and `date` for calendar dates.
- Store monetary values as `numeric(12,2)`, never floating point.
- Store payment-provider references, not card data.
- Use soft business status where history matters. Do not physically delete financial transactions or completed draws.
- Use `created_at` and `updated_at` on mutable business tables.
- Public data is exposed through explicit views or RPCs, never by exposing private profile rows.
- User-owned records reference `auth.users(id)`; application profile data lives in `profiles`.

### `raffle_tickets`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | PK |
| `club_id` | `uuid` | FK `clubs`, required |
| `raffle_id` | `uuid` | FK `raffles`, required |
| `number` | `integer` | required, non-negative |
| `buyer_profile_id` | `uuid` | FK `profiles`, nullable |
| `buyer_name` | `text` | required |

| `buyer_phone` | `text` | nullable |

| `payment_reference` | `text` | nullable |
| `purchased_at` | `timestamptz` | nullable |

| `created_at` | `timestamptz` | required |

Unique constraint: (`raffle_id`, `number`). Ticket numbers are never reused after a confirmed sale. Reservations and their expiry behavior must be implemented server-side, not trusted to the client.

The public raffle flow uses security-definer RPCs instead of exposing buyer columns:

- `get_public_raffle_numbers(club_slug, raffle_slug)` returns only paid numbers and non-expired pending reservations.
- `reserve_public_raffle_numbers(club_slug, raffle_slug, numbers, buyer_name, buyer_email, buyer_phone)` creates pending reservations for up to 10 numbers and sets a 15-minute expiry. It does not process payment.

### `raffle_draws`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | PK |
| `club_id` | `uuid` | FK `clubs`, required |
| `raffle_id` | `uuid` | FK `raffles`, unique |
| `drawn_at` | `timestamptz` | required |
| `method` | `draw_method` | required |
| `winning_number` | `integer` | required |
| `winning_ticket_id` | `uuid` | FK `raffle_tickets`, required |
| `executed_by` | `uuid` | FK `profiles`, required |
| `evidence_url` | `text` | nullable |
| `result_snapshot` | `jsonb` | nullable, immutable evidence |
| `created_at` | `timestamptz` | required |

A draw is append-only. A completed raffle draw cannot be updated or deleted through normal application access. Reversal requires a separate audited administrative process and must not overwrite the original result.

The simulated draw is executed by `draw_raffle_random(raffle_id)`. The security-definer function requires an active club manager, selects one `paid` ticket using PostgreSQL randomness, inserts the immutable draw record, and changes the raffle status to `drawn` in the same transaction. A second draw for the same raffle is rejected.

## 10. Communication and Settings

### `events`

Use `event_type`, `visibility`, `start_at`, `end_at`, `location`, `image_url`, `created_by`, timestamps. Require `end_at >= start_at`.

Migration `011_events.sql` adds club-managed events with member visibility and the public `get_public_events(club_slug)` RPC. Public results include only active-club events marked `public` that have not ended.

### `posts`

Use `club_id`, `title`, `body`, `image_url`, `author_id`, `status`, `published_at`, timestamps. A published post requires `published_at`.

Migration `010_news.sql` adds the table, manager-only writes, member reads, and `get_public_posts(club_slug)`. The public RPC returns only published post content and publication metadata; author profiles and private club data are never exposed.

Migration `013_public_club.sql` adds `get_public_club(club_slug)`, which returns only the public club identifier, name and slug for active clubs.

Migration `015_public_club_links.sql` extends that RPC with the club website and selected social links. Private contact, address and tax fields remain excluded.

The authenticated `/settings` screen edits only `public_name` and public social links. Updates use the existing manager RLS policy; fiscal, address and private contact fields are intentionally excluded.

### `notifications`

Use `club_id`, `title`, `body`, `type`, `target`, `created_at`. The target is a controlled application value; do not accept arbitrary SQL or executable content.

Migration `012_notifications.sql` adds in-app notifications with member reads and manager-only writes. Push delivery and `user_devices` remain separate future work; this block does not register device tokens or send external notifications.

### `user_devices`

Use `id`, `profile_id`, `platform`, `token`, `permission_status`, `last_seen_at`, `created_at`, `updated_at`. Device tokens are private and must be unique per platform/profile where possible.

Migration `014_user_devices.sql` adds owner-only RLS and idempotent device registration support. The application does not send push notifications yet; a provider and platform-specific permission flow must be selected before activating delivery.

### `club_settings`

Use one row per club with module flags: `members_enabled`, `finance_enabled`, `teams_enabled`, `raffles_enabled`, `draws_enabled`, `pools_enabled`, `events_enabled`, `news_enabled`, `notifications_enabled`, `sponsors_enabled`, `tickets_enabled`, `store_enabled`. Default all MVP modules to enabled and future/legal-dependent modules to disabled.

## 13. RLS Model

The following helper functions are security-definer functions owned by a protected database owner. They must set a fixed `search_path` and must not be callable by anonymous users.

```sql
create or replace function public.is_platform_admin()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select coalesce((auth.jwt() -> 'app_metadata' ->> 'platform_admin')::boolean, false);
$$;

create or replace function public.is_club_member(target_club_id uuid)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select public.is_platform_admin()
    or exists (
      select 1
      from public.club_memberships cm
      where cm.club_id = target_club_id
        and cm.profile_id = auth.uid()
        and cm.is_active
    );
$$;

create or replace function public.has_club_role(target_club_id uuid, allowed_roles public.club_role[])
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select public.is_platform_admin()
    or exists (
      select 1
      from public.club_memberships cm
      where cm.club_id = target_club_id
        and cm.profile_id = auth.uid()
        and cm.is_active
        and cm.role = any(allowed_roles)
    );
$$;
```

Enable RLS on every public table. The baseline policy rules are:

- `profiles`: a user may select and update only their own row; club managers receive only the minimum profile fields needed by a permitted workflow through controlled queries.
- `clubs`: active club members may select their club; president and secretary may update administrative data; public data is served by an explicit public view/RPC.
- `club_memberships`: active members may view memberships in their club; president may create/update/delete roles; role changes always create an audit row.
- `memberships`, `membership_fees`, `club_officials`, `teams`, `players`, `team_players`, `team_staff`: club members may select according to role; president, secretary or explicitly authorized managers may mutate according to the feature permission matrix.
- `financial_accounts` and `financial_transactions`: president and treasurer may select; president and treasurer may create; updates are restricted and audited; deletes are denied to normal client roles.
- `raffles`, `raffle_tickets`, `raffle_draws`: authorized club staff may manage; public ticket reads expose only availability and public raffle information; buyer contact fields are never public.
- `events` and published `posts`: public reads are available only through explicit public views/RPCs; private mutations require club roles.
- `notifications`: club staff may create; recipients may read only their own delivered notifications through a future delivery relation.
- `user_devices`: only the authenticated owner may read or mutate their devices.
- `club_settings`: club president may read and mutate; public clients receive only enabled-module flags through an explicit public query.
- `audit_logs`: authorized club managers may read their club audit rows; inserts are performed by trusted functions; updates and deletes are denied.

Every policy must check the row's own `club_id`, or derive and verify it server-side. Never rely on a client-provided club filter alone. Cross-club foreign-key consistency must be enforced with composite keys or trusted triggers.

## 14. Triggers and Server Functions

Required before production use:

1. `set_updated_at` triggers on all mutable tables.
2. `handle_new_user` creates a minimal `profiles` row after Supabase Auth registration.
3. A transaction trigger or trusted RPC updates `financial_accounts.current_balance` and writes audit data.
4. A trusted raffle RPC reserves or confirms a ticket atomically, validates the raffle status and prevents duplicate numbers.
5. A trusted draw RPC locks the raffle, verifies the ticket is paid, inserts exactly one immutable `raffle_draws` row, updates the raffle to `drawn`, and writes an audit row.
6. Cross-club validation triggers for child rows where a simple composite foreign key is not used.
7. Audit triggers or service functions for role changes, financial mutations, exports and draws.

Payment confirmation must come from a verified provider webhook handled by an Edge Function. A browser return URL is never proof of payment.

## 15. Public Data Boundary

Create explicit public views or RPCs for:

- club public profile: `public_name`, logo, city/province, website and social links;
- published club news;
- public events;
- active raffle: title, description, image, price, dates and available numbers;
- ticket purchase confirmation for the requesting buyer only.

Do not expose `tax_id`, address, private notes, date of birth, phone, email, internal IDs beyond what the public route needs, or other buyer records.

## 16. Development Seed

The development seed may create:

- one test club;
- one test season and team;
- test users created through Supabase Auth fixtures;
- one president, one treasurer, one secretary and one member membership;
- sample memberships with non-contiguous member numbers such as 100, 101 and 103;
- one financial account and balanced sample transactions;
- one draft raffle without real payment data.

Never seed production credentials, real personal data, payment secrets or card information.

## 17. Migration Order

1. Extensions, enum types and common functions.
2. Profiles and clubs.
3. Club memberships, officials and settings.
4. Memberships and fees.
5. Seasons, teams, players and staff.
6. Finance tables and balance functions.
7. Raffles, tickets and draws.
8. Communication tables.
9. Audit tables and audit triggers.
